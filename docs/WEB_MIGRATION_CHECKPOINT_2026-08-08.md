## 1. Главное стратегическое решение

«Вместе к цели» считать **одним продуктом**, а не отдельными Android- и веб-приложениями.

Целевая структура продукта:

1. публичный SEO-native сайт;
2. веб-кабинет;
3. PWA как устанавливаемая версия того же веб-продукта;
4. позже браузерное расширение как быстрый вход к текущему действию;
5. Android-приложение как мобильный клиент той же системы;
6. единый аккаунт, единая серверная модель и синхронизация между клиентами.

На текущем этапе **веб является основной развиваемой версией продукта**. Android сохраняется как стабильная контрольная реализация и не должен независимо обрастать новыми крупными функциями до появления общего backend/API.

Это означает:

> один бренд + одна продуктовая логика + несколько интерфейсов.

Пока веб и Android технически не идентичны 1:1, потому что между ними ещё нет общей серверной базы и синхронизации.

## 3. Каноническое обещание продукта

> **Одна цель. Один следующий шаг. Конкретное время. Другой человек рядом. Возможность вернуться.**

Главная задача продукта — не хранить списки дел, а помогать человеку:

- начать важное;
- уменьшить слишком большую задачу;
- выбрать ближайшее действие;
- начать с посильного варианта;
- отметить полный/частичный результат;
- вернуться после остановки;
- определить следующий шаг.

Ключевой ежедневный вопрос:

> **Что мне нужно сделать сегодня?**

## 4. Неизменяемые продуктовые правила

### 4.1. Четыре самостоятельных направления

В продукте существуют четыре независимых направления:

1. **Важная цель**;
2. **Челлендж**;
3. **Дела и задачи**;
4. **Регулярные практики**.

Не сводить их искусственно в одну систему.

### 4.2. 90 дней — только для «Важной цели»

Ориентир примерно на 90 дней относится только к важной цели.

Это не контракт, не блокировка и не запрет менять маршрут.

Не вводить без отдельного решения:

- обязательную семидневную проверку;
- запрет смены цели;
- статусы «тестовая / закреплённая»;
- обязательный глубокий опросник;
- жёсткую парковку целей.

### 4.3. Продукт не наказывает

Не использовать:

- красные провалы;
- обнуление прогресса;
- обвиняющие формулировки;
- давление сериями дней;
- чувство вины как механику возвращения.

После остановки задача продукта — помочь продолжить.

### 4.4. Минимальный вариант не равен полному выполнению

Минимальный шаг нужен для сохранения контакта с задачей, но не должен выдаваться за полный результат.

GitHub Pages — тестовый хостинг. Перед настоящей SEO-индексацией нужен основной публичный домен и правильный `NEXT_PUBLIC_SITE_URL`/canonical.

## 6. Что уже реализовано в веб-MVP

### 6.1. Публичная главная

Главная построена как маркетинговый вход:

- проблема пользователя;
- обещание ближайшего посильного шага;
- отличие от обычного списка дел;
- четыре направления продукта;
- бесплатный мини-инструмент;
- переход в кабинет.

Известный визуальный долг: правый hero preview требует дальнейшей доработки дизайна и контраста. Это не блокирует функциональную разработку.

### 6.2. Гостевой кабинет

Работает без регистрации.

Поддерживает:

- создание важной цели;
- ориентир результата примерно на 90 дней только для важной цели;
- ближайший шаг;
- дела и задачи;
- челленджи;
- регулярные практики;
- текущий фокус;
- полный/частичный/несостоявшийся результат;
- создание следующего шага;
- экспорт/импорт `vmeste-export-v1.json`;
- сохранение после перезагрузки.

### 6.3. Сценарий текущего действия

Добавлен цикл:

- **Начать сейчас**;
- **Начать с минимума**;
- назначить время;
- **Выполнено**;
- **Сделано частично**;
- **Я остановился**;
- продолжить минимальным вариантом;
- назначить время возвращения;
- закрыть подход как «не состоялось».

В модели фиксируются `startedAt` и `plannedAt`. Старые локальные данные нормализуются и продолжают работать.

### 6.4. PWA

Реализованы:

- `manifest.webmanifest`;
- service worker;
- иконки 192/512;
- установка на компьютер/телефон;
- запуск в отдельном окне;
- базовый offline cache;
- start URL в кабинет.

PWA — не отдельный продукт, а способ использовать тот же веб-кабинет.

## 7. SEO-native архитектура

8 августа заложен отдельный SEO-native слой.

Принцип:

> пользователь из поиска должен попадать не обязательно на рекламную главную, а сразу на страницу своей проблемы и получить реальную пользу без регистрации.

Архитектура разделена на пять сущностей:

1. **Problem Page** — редакционная публичная проблема;
2. **Micro Tool** — единый интерактивный движок;
3. **User Session** — приватная пользовательская сессия;
4. **SEO Layer** — metadata/canonical/OpenGraph/sitemap/robots;
5. **Conversion Layer** — переход из бесплатного инструмента в кабинет.

### 7.1. Важное правило приватности

Публичный URL никогда не создаётся из пользовательского текста.

Например текст:

> «Мне завтра надо позвонить Васе и договориться про машину»

остаётся только в браузере пользователя и не становится индексируемой страницей, slug, canonical или sitemap entry.

## 10. Micro Tool

Общий движок находится в:

`web/lib/micro-tool/engine.ts`

Контракт:

`MicroToolGenerator`

Текущая реализация rule-based.

Поддерживаемые действия:

- `first_step`;
- `smaller_step`;
- `next_step`;
- `choose_between_tasks`;
- `two_minute_start`.

Пользовательский сценарий на Problem Page:

> конкретная задача → первый шаг → сделать меньше / следующий шаг / изменить задачу → сохранить шаг → кабинет.

AI пока не требуется. Важное архитектурное решение: позже rule-based генератор можно заменить AI-адаптером с тем же интерфейсом без изменения публичных URL и структуры страниц.

## 11. User Session и Conversion

### User Session

Файл:

`web/lib/micro-tool/session.ts`

Сессия хранится в `sessionStorage` и содержит:

- `problemSlug`;
- `problemType`;
- пользовательскую задачу;
- историю предложенных шагов.

Session ID не попадает в URL.

### Conversion Layer

Файл:

`web/lib/conversion.ts`

После получения пользы пользователь может нажать:

> **Сохранить шаг и продолжить**

Текущий шаг сохраняется через уже существующий `workspace`-слой и появляется в кабинете как активное действие.

Таким образом SEO-страницы не образуют отдельный продукт: они являются входными дверями в тот же «Вместе к цели».

## 12. SEO Layer

Реализованы:

- собственный `title` для каждой Problem Page;
- `meta description`;
- canonical;
- OpenGraph;
- H1;
- человекопонятный slug;
- `sitemap.xml`;
- `robots.txt`;
- статический HTML через `generateStaticParams`.

Публичные Problem Pages генерируются как SSG HTML, поэтому основной текст доступен поисковому роботу без выполнения интерактивного JS.

Индексируются:

- главная;
- опубликованные редакционные Problem Pages.

Не индексируются:

- `/cabinet/`;
- персональные цели;
- пользовательская история;
- session IDs;
- пользовательские результаты;
- технические приватные маршруты;
- URL с query-параметрами.

Кабинет имеет `noindex, nofollow`.

## 16. Следующий этап

Текущий SEO/Micro Tool прототип вручную проверен пользователем и признан работающим.

Следующий логичный порядок:

### Этап A — довести веб-MVP как основной клиент

- устранить оставшиеся заметные UX-проблемы;
- проверить сохранение/возврат/следующий шаг на нескольких реальных сценариях;
- при необходимости улучшить rule-based Micro Tool, но не переусложнять.

### Этап B — реальная аналитика + основной домен

- выбрать основной публичный домен;
- настроить `NEXT_PUBLIC_SITE_URL`;
- убедиться, что canonical указывают на основной домен, а не GitHub Pages;
- подключить Яндекс Метрику/GA4/GTM или другой выбранный сбор событий;
- только после этого начинать реальную SEO-индексацию.

### Этап C — тематический хаб

Когда пять Problem Pages уже находятся на основном домене, создать:

`/procrastination/`

как полезный каталог существующих инструментов, а не пустую SEO-страницу.

### Этап D — общий backend / аккаунт / синхронизация

Это следующий крупный архитектурный переход.

Цель:

> одна учётная запись → одна база → один набор целей/действий → Web/PWA/Android.

Предпочтительная схема:

- Supabase/PostgreSQL;
- авторизация;
- перенос гостевых данных в аккаунт без ручного повторного ввода;
- синхронизация текущего состояния;
- API/репозиторный слой, независимый от интерфейса;
- позже подключение Android к той же модели.

До этого момента считать Web/PWA основной рабочей версией, Android — стабильным мобильным референсом.

## 17. Миграционные требования, которые нельзя потерять

При переходе к серверу:

- пользователь не должен вручную переносить уже созданные данные;
- сохраняется portable export `vmeste-export-v1.json`;
- IDs и timestamps должны быть стабильными;
- импорт должен валидировать данные;
- нужен preview перед импортом;
- нужна защита от дублей;
- нужен backup/undo;
- гостевой local-first сценарий должен продолжать работать до регистрации;
- регистрация не должна стирать гостевое пространство.

Целевая общая модель должна включать минимум:

- User / Workspace;
- Goal;
- Action;
- ActionResult;
- Practice;
- Challenge;
- SupportSession;
- Insight.
